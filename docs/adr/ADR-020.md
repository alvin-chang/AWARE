# ADR-020 — AWARE 2.0 Architecture

**Status:** Proposed  
**Date:** 2026-05-30  
**Author:** Architect (Architect) with Researcher (Researcher) input  
**Supersedes:** ADR-019 (GitOps Agent-as-Code, April 2026) — new major version  
**Build phase:** A1

## Context

AWARE v1 is an autonomous compliance infrastructure for AI agents — cryptographic identity, T0-T4 constraint levels, pheromone-based routing, distributed revocation. It ships as a 2-service Docker Compose stack (backend + frontend, ~185 files).

AWARE 2.0 pivots from compliance infrastructure to **self-improving agent framework**: a portable, domain-adaptable autonomous agent (like Claude Code/Cursor) that continuously improves via two RL pipelines. The vision is "Adaptive Workflow Agent with Recursive Evolution."

**The architectural problem:** How do we build a self-improving agent that trains itself continuously while remaining portable, compliant, and operable offline?

**The insight:** AWARE v1 already has the compliance infrastructure and the agent host architecture. AWARE 2.0 adds the learning loop — two complementary training pipelines that close the feedback loop between agent performance and model improvement.

## Two-Pipeline Architecture

AWARE 2.0 uses two independent, complementary training pipelines:

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    AWARE 2.0 — DUAL-TRAINING ARCHITECTURE               │
│                                                                         │
│  ┌─────────────────────────────────┐  ┌─────────────────────────────────┐│
│  │  AZR SELF-PLAY (Internal RL)   │  │  META CLAW (External RL)        ││
│  │                                 │  │                                 ││
│  │  Proposes synthetic tasks       │  │  Learns from real user          ││
│  │  (code/math/security)           │  │  conversations                 ││
│  │  ↓                              │  │  ↓                              ││
│  │  Verifies outcome correctness   │  │  PRM judge scores per-turn     ││
│  │  (Python executor)              │  │  (reasoning quality)           ││
│  │  ↓                              │  │  ↓                              ││
│  │  Generates preference pairs   │  │  Extracts preference pairs     ││
│  │  from self-play outcomes       │  │  from reasoning quality deltas ││
│  │  ↓                              │  │  ↓                              ││
│  │  DPO fine-tune (Modal GPU)      │  │  DPO fine-tune (cloud GPU)      ││
│  │  $3K Modal budget               │  │  $1K dialogue POC budget       ││
│  │  Runs autonomously in bg        │  │  Runs on conversation batch    ││
│  └─────────────────────────────────┘  └─────────────────────────────────┘│
│                      ↘                        ↙                           │
│               Both feed into                                          │
│               shared weight store                                     │
│               (Qwen 2.5 7B base)                                     │
│                      ↓                                                 │
│  ┌─────────────────────────────────────────────────────────────────────┐│
│  │  COORDINATOR SESSION — persistent, holds <meta-rl-pipeline> context        ││
│  │  Task workers run in parallel (lightweight threads, not procs)   ││
│  │  Serves via: MiniMax API (online) or Ollama (offline)             ││
│  │  Complies via: T0-T4 constraint layer from AWARE v1             ││
```

**The strategic differentiator:** No competitor does both internal self-play AND external conversation-grounded RL with frontier model evaluation. That's the core moat.

## Decision 1: Agent Session Model

**Chosen: Persistent coordinator + lightweight concurrent task workers — not isolated sub-agents, not single monolithic session.**

### Why the dichotomy is false

| Option | Problem |
|--------|---------|
| Current <runtime> sub-agents | Heavyweight isolated sessions. Each has its own context, tools, memory. Spawn cost is significant. Right for fault isolation, wrong for persistent learning. |
| Single persistent session | Simpler state, but context-window pressure, no parallelism, single point of failure. Loses <meta-rl-pipeline>'s persistent conversation context — the learning signal requires a coherent history. |
| **AWARE 2.0 model** | **Persistent coordinator** holds <meta-rl-pipeline> conversation loop + learning state. Task execution is parallelized via lightweight **task workers** within the same process (goroutine-style threads, not separate processes). AZR self-play runs entirely **off-session on Modal GPU** — doesn't need to be in the agent's session at all. |

### Protocol

1. Coordinator receives user request
2. Coordinator spawns task workers for parallel execution (code gen, research, tool calls)
3. Workers are interruptible, cancellable, pooled
4. Coordinator integrates results and maintains conversation history
5. Conversation history feeds <meta-rl-pipeline> pipeline for learning

This design satisfies:
- Persistent conversation context for <meta-rl-pipeline> learning loop ✅
- Horizontal scaling via worker pool ✅
- Fault isolation at task level, not session level ✅
- No costly sub-agent spawn overhead for routine tasks ✅

## Decision 2: Training Pipeline Integration

**Chosen: AZR outcome filter gates <meta-rl-pipeline> process training — signals are NOT merged at the reward level.**

### Why reward signal merging is fragile

<meta-rl-pipeline> (process-RL) and AZR (outcome-RL) optimize for different things:
- **<meta-rl-pipeline>:** *How* the model reasons — coherence of reasoning chain, revision quality
- **AZR:** *Did the task succeed* — binary/scalar outcome (pass/fail, completion score)

A model can reason well and fail, or reason poorly and succeed by accident. When outcome and process signals conflict, naive averaging creates reward hacking.

### Integration architecture

```
AZR outcome signal (pass/fail)
       ↓
  Outcome filter ──→ used to SELECT good process examples
       ↓
<meta-rl-pipeline> process training on filtered data
```

Specifically: AZR tells us which task-completion examples are **valid** (outcome = success). We use that to filter which conversation examples <meta-rl-pipeline> trains on. The resulting model learns reasoning patterns *that are known to produce successful outcomes* — without the reward conflict.

**When outcome directly overrides process:** Ambiguous failures (definite failure, security violation, crash). These are hard negatives in preference training.

### Training algorithm: DPO over PPO

| Algorithm | Why |
|-----------|-----|
| **DPO (Direct Preference Optimization)** | Simpler, more stable, 50% less GPU time than full RL, mature tooling (TRL, training-optimizer, Axolotl). Converts self-play to preference pairs — supervised-style, no reward model needed. |
| PPO (TRR++ / original AZR) | Requires full veRL infrastructure, custom advantage estimators. Not feasible on single-GPU budget. |
| SFT alone | Doesn't learn from mistakes; can overfit to high-scoring patterns. |

**Budget allocation:**
- ~$3K for AZR DPO training on Modal (A100-80GB, ~60 GPU hours = ~$150, leaving $2,850 buffer)
- ~$1K for SOTA dialogue POC (per-turn PRM evaluation with Claude Haiku, ~16,600 sessions)
- ~$1K reserve

## Decision 3: Serving Stack

**Chosen: Docker Compose (7 services) + Ollama sidecar + MiniMax API as primary online model.**

### Services

| Service | Port | Purpose |
|---------|------|---------|
| `aware-gateway` | 3000 | API gateway (replaces current backend) |
| `aware-frontend` | 3001 | React UI (unchanged) |
| `aware-coordinator` | 8100 | Persistent coordinator session + task worker orchestration |
| `aware-worker` | — | Task workers (scaled horizontally, 2+ replicas) |
| `ollama` | 11434 | Local model inference (offline mode) |
| `aware-memory` | 8200 | Redis (agent memory, session store) |
| `aware-trainer` | — | Modal training poller (background daemon) |

### Mode switching

```
MODE=online  → MiniMax API (primary), Ollama fallback (hybrid only)
MODE=offline → Ollama only (strict offline)
MODE=hybrid  → MiniMax primary, Ollama automatic fallback
```

In offline mode, Ollama must have models pre-pulled. Required models:
- `qwen2.5:7b` (~4.7GB) — general reasoning
- `nomic-embed-text:latest` (~274MB) — embeddings for RAG

### Dockerfile split

Current v1 has a single Dockerfile building everything. v2.0 splits into per-service images:
- `Dockerfile.gateway` — API gateway (extracted from current backend)
- `Dockerfile.coordinator` — Coordinator service
- `Dockerfile.worker` — Task workers
- `Dockerfile.trainer` — Modal training poller
- `Dockerfile.training` — Modal GPU training image (CUDA-based, separate from compose)

### Weight update mechanism (Modal → Coordinator)

```
1. Modal training job completes → writes weights to Modal volume
2. aware-trainer polls Modal every 5 min, detects new checkpoint
3. Trainer validates weights (checksum + sanity inference)
4. Atomic symlink swap: /app/weights/latest -> /app/weights/run-{timestamp}/
5. Coordinator detects symlink change → hot-reloads without restart
6. Workers pick up new weights on next task assignment (read-only mount)
```

**Chosen: Single curl|bash installer, no VM, no cloud dependency, works offline.**


**Offline capability:** With `MODE=offline` and Ollama models pre-pulled, AWARE 2.0 runs without internet. Suitable for air-gapped deployment.

## Decision 5: <meta-rl-pipeline> PRM Integration + HeavySkill Reasoning Layer

**Chosen: Per-turn evaluation with Claude Haiku for routine scoring + Sonnet for ambiguous cases, enhanced by HeavySkill (arXiv:2605.02396, May 2026) test-time reasoning.**

### What is HeavySkill?

HeavySkill is a two-stage test-time reasoning technique:
1. **Parallel Reasoning** — generate K independent reasoning attempts
2. **Heavy Reasoning** — deep single-threaded refinement of the best attempt

It runs at inference time (not training time), so it doesn't consume Modal GPU budget. But its outputs — richer reasoning traces with explicit refinement — become training data for the DPO pipeline.

**The two improvement axes:**
- **Training-time** (AZR + <meta-rl-pipeline>): model improves between inference calls
- **Test-time** (HeavySkill): model improves *within* a single inference

These are complementary. HeavySkill makes each inference better; AZR/<meta-rl-pipeline> make the model better across all inferences.

### Integration points

#### 1. PRM evaluation → HeavySkill-enhanced scoring

Current: single-pass reasoning → PRM score → preference pair

With HeavySkill:
```
Agent reasoning attempt
       ↓
  ┌────────────────────────────────────────┐
  │  PARALLEL REASONING (K attempts)       │
  │  [Attempt 1] [Attempt 2] ... [Attempt K]│
  │  ↓         ↓              ↓            │
  │  PRM_1    PRM_2          PRM_K          │
  │  (Haiku,  (Haiku,        (Haiku,        │
  │   cheap)   cheap)         cheap)        │
  └──────────────┬─────────────────────────┘
                 │
            pick best (PRM_max)
                 │
       ┌────────▼────────┐
       │  HEAVY REFINEMENT │
       │  Deep single-pass  │
       │  refinement of     │
       │  best attempt      │
       │  (PRM_h > PRM_max) │
       └────────┬────────┘
                │
           refined trace
                │
       ┌────────▼────────┐
       │  PREFERENCE PAIR │
       │  chosen = refined │
       │  rejected = best  │
       │  initial attempt  │
       └──────────────────┘
```

The natural preference pair: initial-best-attempt (rejected) vs. heavy-refined (chosen). This structure is already aligned for DPO — no extra annotation needed.

#### 2. AZR PROPOSE phase → diverse task variants

Before the learnability filter, the Proposer generates K parallel task proposals. Each undergoes executor validation. K attempts → diverse task distribution → filter for learnable tasks.

```
Proposer generates K task variants:
  [τ₁] [τ₂] ... [τ_K]
         ↓
  Executor validates each (can produce valid (x, y*)?)
         ↓
  Keep: valid + learnable (pass rate 5-95%)
  Discard: degenerate or impossible
```

Diversity in proposal → robustness in training corpus.

#### 3. DPO training data → implicit preference pairs from HeavySkill

The heavy refinement vs. initial attempt comparison is a preference pair without annotation overhead. This enriches the DPO dataset without extra human labeling.**

### PRM judge format

```
SYSTEM: You are a reasoning quality evaluator. Score the agent's reasoning
on each turn. Focus on reasoning process, not outcome.

USER: [conversation context up to turn N]
AGENT TURN N:
<reasoning>{agent's chain-of-thought}</reasoning>
<response>{agent's visible response}</response>
TASK CATEGORY: {code-generation|research|security-review|...}
EXPECTED OUTCOME: {success|partial|failure|unknown}

Evaluate reasoning quality 1-10:
- 1-3: Flawed logic, hallucination, irrelevant reasoning
- 4-6: Adequate but incomplete, minor gaps
- 7-8: Strong reasoning, clear structure
- 9-10: Excellent, anticipates edge cases, self-corrects

Return JSON: { "score": 7, "strengths": [...], "weaknesses": [...], "confidence": 0.85 }
```

### Cost estimation (with HeavySkill)

| Model | Cost/attempt | K attempts | Heavy refinement | Cost/session (15 turns) | Sessions per $1K |
|-------|-------------|------------|-----------------|--------------------------|-----------------|
| Claude Haiku | ~$0.003 | K=4 | ~$0.01 | ~$0.19 | ~5,200 |
| primary chat model | ~$0.012 | K=2 | ~$0.02 | ~$0.08 (ambiguous only) | ~12,500 |

**Strategy:** Haiku for all K parallel attempts (cheap). Sonnet only for heavy refinement on sessions flagged as ambiguous (score variance > 2 between consecutive turns). K=4 parallel attempts strikes balance between diversity and cost.

**Compute cost at test-time:** HeavySkill runs at inference — every inference now does K parallel attempts instead of 1. This is K× inference cost but captures the reasoning quality improvement. For a $1K budget at ~$0.19/session = ~5,200 sessions. If we reduce K to 3 (cheaper), sessions = ~6,900.

### AWARE v1 integration

Existing AWARE v1 components that <meta-rl-pipeline> requires:

| Component | Location | Reuse |
|-----------|----------|-------|
| Reinforcement controller | `src/routing/reinforcement-controller.js` | PRM score replaces `evaluateQuality()` output |
| Quality evaluator | `src/routing/quality-evaluator.js` | Maps PRM scores to pheromone reinforcement |
| Pheromone table | `src/routing/pheromone-table.js` | Quality-weighted reinforcement (existing ADR-011) |

**Key insight:** <meta-rl-pipeline> does NOT replace the existing reinforcement plumbing. It **feeds it better quality signals** — per-turn PRM scores instead of coarse outcome metrics. This creates a closed loop:

```
Better reasoning → higher PRM scores → stronger pheromone reinforcement
     ↑                                          ↓
     └──── better model weights ←── DPO training
```

### T0-T4 mapping

HeavySkill operates at **T2 (reasoning validation)** — it validates and refines the agent's reasoning within a single inference. <meta-rl-pipeline>'s PRM evaluation is the measurement signal; HeavySkill is the reasoning mechanism that produces better traces to measure.

| Level | Description | <meta-rl-pipeline>/HeavySkill relevance |
|-------|-------------|-------------------------------|
| T0 | Fully human-controlled | N/A |
| T1 | Human-in-the-loop with policy gates | PRM informs human review |
| **T2** | **Automated reasoning validation** | **HeavySkill + PRM: parallel attempts → refinement → measurement** |
| T3 | Autonomous with cryptographic identity | Fine-tuned models with agent NHI |
| T4 | Full autonomous operation | Self-improving loop without intervention |

**Chosen: Ollama as a separate container (sidecar), not embedded in the gateway.**

## Decision 7: Shared Reasoning Layer — HeavySkill as Universal Primitive

**Chosen: HeavySkill as a shared reasoning primitive available to all agents via a common library, not just AWARE.**

### The insight

HeavySkill (K parallel attempts → deep refinement) is not specific to AWARE's training pipeline. It's a general reasoning primitive that any agent can use for any problem. Making it a **shared library** means every agent gets access to the same high-quality reasoning tool — without each having to implement it themselves.

This is analogous to how `exec()` is a universal tool: all agents call it, nobody rewrites it. HeavySkill should be the same: a system-provided reasoning primitive.

### API: `heavy_think(problem, K_attempts, task_type)`

```javascript
// Shared reasoning primitive — available to all agents
heavy_think({
  problem: string,           // The task or question
  K_attempts: number,        // Parallel reasoning attempts
  task_type: enum,           // 'standard' | 'security' | 'financial' | 'creative'
  context: object            // Additional context (codebase, KB, conversation history)
}) → {
  refined_trace: string,     // Deep refinement result
  confidence: number,        // 0-1 confidence score
  attempts: [{               // All K attempts for audit/training
    reasoning: string,
    prm_score: number,
    selected: boolean
  }],
  verification: {
    passed: boolean,
    method: 'exec' | 'test_suite' | 'citation_check' | 'kg_consistency'
  }
}
```

### K configuration by criticality

| Task type | K | Rationale |
|-----------|---|----------|
| Simple/routine | 2 | Low diversity needed, cost-sensitive |
| Standard/complex | 3-4 | Balance of quality vs. cost |
| Critical (security, financial) | 5-8 | High stakes, need maximum coverage |
| Creative/open-ended | 2-3 | Diversity matters, refinement less relevant |

### Integration points by agent

| Agent | HeavySkill use case |
|-------|---------------------|
| **the coordinating agent** | Task decomposition planning — explore multiple decomposition paths before committing |
| **Researcher (researcher)** | Parallel hypothesis exploration — K different research directions simultaneously |
| **Coder (coder)** | Parallel implementation approaches — K different ways to solve the same problem |
| **Reviewer (reviewer)** | Parallel security attack scenarios — K attack vectors to test |
| **Tester (tester)** | Parallel test case generation — K different test strategies |
| **Chronicler (scribe)** | Parallel documentation outlines — K structural approaches |
| **Auditor** | Parallel compliance checks — K different regulatory frameworks |
| **MemoryStone** | Parallel KG query paths — K different traversal strategies |
| **<meta-rl-pipeline>** | Parallel PRM evaluation paths — K reasoning traces for scoring |

### Verification layer (per-system)

Each `heavy_think` call includes a verification step appropriate to the task type:

| Task domain | Verification method |
|-------------|---------------------|
| Code generation | Python exec / test suite execution |
| Bug bounty | Testnet execution + sandbox |
| Research | Source citation + cross-consistency check |
| Memory/KG | Knowledge graph consistency validation |
| Financial | Formal audit trail + constraint verification |
| Security | Red team attack simulation |

### Implementation

- **Library location:** `<runtime-source>/skills/shared/heavy-think/` (shared across all agents)
- **Per-agent integration:** ~50-100 lines per agent as a tool call (similar to how `exec()` is a tool)
- **Caching:** Results cached in MemoryStone for training data (preference pairs from HeavySkill are DPO-ready)
- **K configuration:** Set at call site, default varies by agent type

### Training data pipeline

Every `heavy_think` call generates training data automatically:
```
heavy_think(problem) → K attempts + refined trace
                            ↓
                     preference pair:
                       chosen = refined trace
                       rejected = best initial attempt
                            ↓
                     MemoryStone JSONL
                            ↓
                     DPO training batch
```

No additional annotation needed — the reasoning quality comparison is inherent in the HeavySkill process.

### HeavySkill in the learning loop

```
Inference time (test-time compute):
  User prompt → K parallel reasoning attempts → pick best → heavy refinement → response
                         ↓                                              ↓
                   all K attempts                                 refined trace
                   logged to session                               logged to session
                         ↓                                              ↓
                   PRM scores (K)                              PRM score (refined)
                         ↓                                              ↓
                   best = initial attempt                         chosen = refined
                   (rejected in DPO pair)                          (in DPO pair)

Training time:
  Preference pairs (refined > initial) → DPO fine-tune → updated weights
```

## Alternatives Considered

### 1. Single persistent session (rejected)
Context window pressure, no parallelism, single point of failure. Loses <meta-rl-pipeline> learning signal.

### 2. Reward signal merging (rejected)
Creates reward hacking when process and outcome signals conflict. Filter approach is cleaner.

### 3. veRL framework for DPO training (rejected for POC)
Requires 4×A100-80GB for 7B. Single A100-80GB with training-optimizer 4-bit QLoRA fits our budget.

### 4. Kubernetes for coordinator (rejected)
Contradicts N.O.M.A.D. portability principle. k8s-manifest is extended for enterprise deployments only.

### 5. SQLite for memory service (rejected)
Write contention under concurrent worker access. Redis data structures map directly to AWARE's needs.

## Consequences

**Positive:**
- Self-improving agent framework (not replicated by competitors)
- Two complementary RL pipelines provide durable competitive moat
- Portability (curl|bash install) enables broad distribution
- T0-T4 compliance framework is unique in agent infrastructure space
- Modal training budget is sufficient for meaningful POC

**Negative:**
- Significant implementation complexity (16 new files, new ML infrastructure)
- Python/Node.js language boundary requires careful interface design
- <meta-rl-pipeline> requires <runtime> session hook that may not yet exist
- Modal credit is finite — training efficiency is critical

**Tradeoffs:**
- Complexity vs. capability: 4-month build is justified by the capability jump
- Offline quality vs. online capability: hybrid mode provides graceful degradation
- Budget vs. ambition: the $5K credit is a proof-of-concept budget, not a production budget

## Revisions

### R1 (2026-06-12) — Base model: Qwen 2.5 7B → Qwen 3 8B + Modal SDK client implemented

**Trigger:** The Phase 3 follow-up at commit `c572bfd`+1 replaced
the `unsloth/Qwen2.5-7B-Instruct-bnb-4bit` base with the official
`Qwen/trained-model` checkpoint and implemented the previously-stubbed
`src/trainer/modal-client.js` SDK wrapper.

**Reasoning:**
- **Qwen 2.5 7B** was released September 2024 and is now 21 months
  old. Qwen 3 (April 2025) shows meaningful reasoning improvements
  on the security-domain prompts that AWARE's preference pairs
  come from.
- **No training-optimizer pre-quantized trained-model exists on Hugging Face**
  (verified by HF API query). The 4-bit loading path was therefore
  switched from `FastLanguageModel.from_pretrained(load_in_4bit=
  True)` to a direct `transformers + BitsAndBytesConfig` + `peft.
  get_peft_model` path. training-optimizer 2025.4.1 still provides the
  training-speed benefit on the QLoRA attach step.
- **Modal SDK client** (`modal-client.js`) was previously
  flagged as a code-gap in Phase 3 closure. The stubbed SDK call
  sites are now real `modal.Function.from_training_script` and
  `FunctionCall.from_id` calls. This is a pure code change; no
  new operator dependencies.

**Impact:**
- Job timeout 14400s → 18000s (Qwen3 trains ~30% slower than
  Qwen2.5 at ctx=4096; 5h gives 25% slack for a 10K-pair run).
- `max_seq_length` 2048 → 4096 (Qwen3 has better long-context
  attention; matches ADR-020 Decision 2 envelope).
- Dependency bump: unsloth 2024.10.7→2025.4.1, trl 0.11.4→0.15.0,
  transformers 4.45.2→4.51.0, peft 0.13.2→0.14.0, bitsandbytes
  0.44.1→0.45.0, accelerate 1.0.1→1.1.0. torch stays at 2.4.1
  (2.5/2.6 broke some training-optimizer paths).
- VRAM budget: trained-model at 4-bit ≈ 6GB weights + ~18GB for
  activations + LoRA grads at batch=4, ctx=4096 ≈ **24GB used
  out of 80GB A100-80GB**. 70% headroom. No regression vs
  Qwen2.5-7B's footprint.

**Not changed:** the original Decision 2 budget envelope
(~$3K for 60 GPU-hours) is unchanged. The coordinator
inference model (`qwen2.5:7b` via Ollama) and the <secondary-llm>
fallback (`fallback model`) are independent decisions outside
this revision.
