# ADR-021 — Configuration System

**Status:** Approved
**Date:** 2026-06-12
**Author:** the AWARE maintainers
**Supersedes:** None — first config-system ADR
**Build phase:** A1 (Phase 1 close-out polish)

---

## Context

AWARE 2.0 Phase 1 (commit `880a47c`) introduced three new v2 services: coordinator, gateway, and a model router. Across the v2 source, **14 ad-hoc `process.env.*` reads** were scattered:

- `src/coordinator/http-server.js` — 5 reads (PORT, HOST, REQUEST_TIMEOUT_MS, REQUEST_COST_CAP_USD, KILL_SWITCH)
- `src/coordinator/index.js` — 4 reads (AWARE_MODE, OLLAMA_URL, <redacted-credential-name>, AWARE_HEAVY_THINK_PATH)
- `src/gateway/server.js` — 5 reads (GATEWAY_PORT, GATEWAY_HOST, PROXY_TIMEOUT_MS, COORDINATOR_URL, GATEWAY_KILL_SWITCH)

This created three concrete problems:

1. **No single source of truth.** Same key (`COORDINATOR_URL`) was read in two places; the resolution was inlined in the consumer.
2. **No validation at module load.** A bad `AWARE_MODE=hybriad` (typo) would only fail at first request, deep inside a request handler.
3. **No redaction discipline.** Anywhere a config dump was needed (debug, telemetry), secret values would be serialized unless each consumer remembered to redact.

**The architectural problem:** How do we make AWARE 2.0's configuration explicit, validated, debuggable, and secret-safe — without slowing down the inner loop?

**The insight:** A small, lazy-getter, in-process config module solves all three problems with zero runtime overhead and one new file.

---

## Decision

**Adopt a single, centralized, lazily-evaluated config module at `src/config/index.cjs`.** Every v2 service reads its configuration through `config.x.*` accessors. Direct `process.env.*` reads for v2-owned keys are forbidden.

### Namespaces

The config module exposes four top-level namespaces plus a `warnings` array:

| Namespace      | Owns                                                              | Read by                          |
|----------------|-------------------------------------------------------------------|----------------------------------|
| `coordinator`  | port, host, requestTimeoutMs, requestCostCapUsd, killSwitch       | `src/coordinator/http-server.js` |
| `gateway`      | port, host, proxyTimeoutMs, coordinatorUrl, killSwitch            | `src/gateway/server.js`          |
| `model`        | mode, minimaxKey, minimaxHost, ollamaUrl                          | `src/coordinator/index.js`       |
| `heavyThink`   | path (sibling-repo path; no per-property env vars at this layer)  | `src/coordinator/index.js`       |
| `warnings`     | soft validation issues (not hard failures)                        | startup logs                     |

Each property is a **lazy getter** that re-reads `process.env` on every access. This preserves two patterns:

- **Test overrides** — tests can mutate `process.env.X` between calls and see the new value (e.g., kill-switch tests).
- **Immediate kill-switch toggling** — flipping `AWARE_KILL_SWITCH=1` takes effect on the next request, no restart.

### Validation

`config.validate()` is called at module load (in `src/gateway/server.js`) and re-callable from any consumer. It throws on:

- `mode=online` but `<redacted-credential-name>` is unset (hard fail — no API key to call)
- `GATEWAY_PORT === COORDINATOR_PORT` (must differ — they'd collide)
- Invalid `mode` enum (`online`, `hybrid`, `offline`)
- Out-of-bounds port (`<0` or `>65535`)
- Non-numeric / non-finite values where a number is required
- Numeric out-of-range where a finite range is required

Soft issues (e.g., `<redacted-credential-name>` not set in `hybrid` mode, `AWARE_MODE=offline` but no `OLLAMA_URL`) accumulate into `config.warnings()` and are logged at startup but do not throw.

### Redaction

`config.snapshot()` returns a plain object suitable for debug dumps. Secret keys (`<redacted-credential-name>`, `POSTGRES_PASSWORD`, `GITEA_TOKEN`, etc.) are replaced with `<redacted length=N>` — the value is never serialized, but the key shape is preserved so debug output stays readable.

### CJS vs ESM

The config module is `src/config/index.cjs` (CommonJS, `.cjs` extension). This was a deliberate choice after the ESM/CJS interop failure during initial Docker build:

- `src/gateway/server.js` is CJS (`require()`) → needs `module.exports` shape.
- `src/coordinator/http-server.js` is ESM (`import`) → Node's CJS-to-ESM interop handles both directions.
- Renaming to `.cjs` forces Node to parse it as CommonJS regardless of the package's `"type"` field in `package.json`.

`module.exports` is the export shape. Coordinator's `import config from '../config/index.cjs'` works because Node interops CJS default exports.

### Backward compatibility

- All v2 env-var names are unchanged. Existing `docker-compose.coordinator.yml` and `env_file: <credential-store>/credentials.env` work without modification.
- The defaults preserved at the config layer match the prior `process.env.* ?? default` behavior exactly (verified by 18 config tests + 97 unit tests + bring-up).
- v1 source (`src/server.js`, `src/api/`, `src/audit/`, `src/routing/`, `src/ui/`) is untouched per the v1 boundary rule.

## Alternatives considered

### A. Per-file config

Each service defines its own `config.js`. **Rejected** because it doesn't solve the "no single source of truth" problem — the validator would have to be re-implemented three times, and snapshot/redaction logic would be duplicated.

### B. External config file (YAML/TOML)

Add `aware.config.yaml` and a loader. **Rejected** because:

- Adds a new file format to the deployment surface (Docker images must copy it in, env var overrides would still be needed for secrets).
- Yaml parsing is slow at startup and adds a dependency.
- The runtime env is already the source of truth for secrets; a YAML file would shadow that, not replace it.

### C. Keep `process.env.*` scattered (status quo)

**Rejected** because the problems above (no validation, no redaction, no source of truth) are real and already caused one bug this turn (`COORDINATOR_URL` referenced in a `console.log` after being refactored to a function). The fix was a one-line patch, but the *class* of bug — partial refactor leaving a stale reference — is exactly what a centralized config prevents.

---

## Consequences

**Positive:**

- One file (`src/config/index.cjs`) is the source of truth for v2 config.
- Validation runs at module load; bad config fails fast, not at first request.
- Snapshot dumps are secret-safe by default.
- Test override pattern still works (lazy getters + env mutation).
- 18 config tests + 97 total unit tests pass; bring-up reproducible end-to-end with `--profile full`.

**Negative:**

- One more file to keep in sync if env-var names change. Mitigated by `config.x.*` accessor pattern making the search trivial.
- CJS extension (`index.cjs`) is a slight cognitive overhead. Mitigated by README and an inline comment in the module.

**Neutral:**

- v1 source continues to use `process.env.*` directly. Migrating v1 to the new config is out of scope for this ADR.
- Env-var names are unchanged. Operators don't need to update their deployment scripts.
